TEAM SUMMARY
The approved service-request flow is implemented locally. A community member can
submit a service request and track it in My Requests. A verified assistant with
completed training can accept it, start it in Active Jobs, and complete it.
Completed Jobs and the member's My Requests show the saved status on Refresh.
Owners can cancel only while a request is open and unassigned.

IMPORTANT: Migration 004 has NOT been applied to the live Supabase project.
No commits, pushes or deployment were performed. The live website will need the
migration and updated frontend before this feature is ready for real users.

IMPLEMENTATION
- Accessible service request dialog with category, description, location,
  preferred date/time, urgency and optional additional information.
- Required fields, length limits, whitespace checks and SAST date validation.
- Loading/error feedback; failed submission retains entered details. Retrying
  unchanged details uses the same UUID to avoid duplicate creation after a lost
  response. A new edit starts a new submission identity.
- Saved requests, available requests, active jobs and completed jobs use Supabase.
- Refresh, Previous/Next pagination (50 records), filters on the current page,
  confirmation before transitions, and safe text rendering for user content.
- Assistant dashboard reads actual account eligibility and provides workflow links.
  Availability remains read-only. Developer previews cannot elevate permissions.
- Relevant community/assistant links and script filenames repaired.
- Resource/problem request cards honestly show that those features are not ready.

DATABASE AND PERMISSIONS
New migration: shared/supabase/migrations/004_service_request_workflow.sql
RPCs: create_service_request, accept_service_request, cancel_service_request,
      start_service_request, complete_service_request.
- Server derives identity from auth.uid(); no client-supplied owner/role accepted.
- Creation requires actual community_user role and validates all request fields.
- Accept requires verified + completed training; self-acceptance is forbidden.
- Only the assigned, still eligible assistant can start or complete a job.
- Row locks and the unique request assignment constraint protect acceptance;
  request/assignment changes occur together and roll back together on error.
- Identity-bound private helpers replace recursive request/assignment RLS reads.
- Browser roles get SELECT only on requests/assignments; writes use these RPCs.
  Resource/problem workflows will need their own controlled write implementation.
- Reusing a creation UUID requires the same owner and unchanged request fields.

5. AUTHENTICATION IMPLEMENTED
Registration: required names/email/password; optional phone; 8-character minimum;
matching confirmation; native validation and accessible labels/autocomplete;
in-flight submission protection; only first_name/last_name/phone metadata sent.
Existing trigger owns profile creation and default community_user role.
With confirmation enabled, show check-email state; with an immediate session,
load trusted state and route. Duplicate-account responses stay generic.
Login: signInWithPassword; invalid/unconfirmed/network/rate-limit errors; verify
identity using getUser; load trusted profile, assistant state and own developer row.
Logout: SDK signOut(scope local), hide protected UI, clear developer/recovery state,
return to login. This signs out this browser; other devices are not explicitly revoked.
Session: SDK persistence/refresh; centralized state loading; auth callbacks avoid
async SDK calls inside the SDK lock; history/foreground pages recheck access.
Email confirmation: dedicated callback, SDK implicit flow, URL cleanup, invalid-link
messages, resend action on login. Standard Supabase ConfirmationURL templates expected.
Forgot password: generic check-inbox success, deployed base-aware reset redirect.
Reset: PASSWORD_RECOVERY event, user-bound 30-minute recovery UI state, refresh
support, updateUser password change, validation and sign-out on success. A normal
session alone does not show this form. Recovery marker grants no database permission.

6. ROUTING / GUARDS / ACCESS MATRIX
Public: index, login, register, forgot-password, confirmation shell, recovery shell.
Community: all community-user HTML pages use trusted community destination access.
Assistant: all assistant HTML pages require verified AND completed assistant state.
Admin: all admin HTML pages require trusted profile role admin.
Developer selector/switcher: own authenticated UUID must exist in developer_accounts.
Developer-selected interfaces may be previewed; RLS still uses the actual account.
Normal routing: admin first; otherwise verified/completed assistant; otherwise
community (including pending assistants/organisation role with no separate UI yet).
Missing session routes to login. Wrong interface routes to trusted destination.
Query failure/missing profile/unsupported role leaves protected content hidden and
shows retry/sign-out controls. No privilege is inferred from query strings or storage.
Navigation is derived from shared/frontend/navigation.js URL, preserving /Community_Services/.
No untrusted return URL is accepted. Empty legacy dashboard URLs are guarded aliases.

7. DEVELOPER MODE
First developer login -> developer.html unless a valid user-bound sessionStorage
view is remembered. Key: community-services.developer-view. Values: community_user,
assistant, admin, or normal (Exit Developer Mode). Developer membership is always
verified before a stored view is honored. Non-developers gain nothing by forging it.
Selection changes navigation/presentation only. There are no profile role writes.
Floating left-bottom bow button opens a native dialog: keyboard focus containment,
Escape, close, focus restoration, mobile sizing. Exit returns to trusted real-role
interface; it does not sign out, delete membership or change actual authorization.
Selector rebuilding is idempotent after a foreground/access recheck.
Developer account provisioning remains a trusted SQL/admin task; README has a generic
YOUR_USER_UUID example. No actual developer identity is committed.

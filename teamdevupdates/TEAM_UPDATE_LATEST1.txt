A Supabase project has been created.

authentication. - GitHub Pages production URL has been configured for
authentication redirects/site URL. - Local development redirect URLs

Environment configuration: - .env is used locally/server-side for

Expected environment variable names:

SECURITY: - SUPABASE_SECRET_KEY is backend/server-side only. - Never
expose SUPABASE_SECRET_KEY in HTML or frontend JavaScript. - GitHub
Pages/frontend code may use the Supabase project URL and publishable
key. - RLS remains the real database security boundary for browser
access.

  -----------------------------------------
  MIGRATION 001 - INITIAL DATABASE SCHEMA
  -----------------------------------------

Created core application tables: - profiles - assistants - requests -
donations - donation_images - assignments - reports - notifications

Important relationships:

auth.users -> profiles

profiles -> assistants / requests / donations / reports / notifications

requests + assistants -> assignments

donations -> donation_images

The authenticated Supabase user UUID is the trusted identity source.

Do not trust a user_id supplied by frontend JavaScript when
authorization can instead be derived from the authenticated Supabase
session.

  ----------
  PROFILES
  ----------

profiles.id corresponds directly to auth.users.id.

Current application roles: - community_user - assistant - admin -
organisation

Normal public registration MUST NOT be allowed to select or assign an
administrator role.

An automatic auth.users trigger creates a profiles row when a new
Supabase Auth user is created.

Normal signup creates: role = community_user

Public signup metadata cannot promote the new user to admin.

  ------------
  ASSISTANTS
  ------------

Assistant records are stored separately from profiles.

Verification status values: - pending - verified - rejected - suspended

Training status values: - not_started - in_progress - completed

Availability values: - available - unavailable

Unverified assistants must not be allowed to accept protected service
jobs.

Assistant verification/training status must not be trusted from browser
state alone.

  ----------
  REQUESTS
  ----------

Request types: - resource - service - problem

Request status values: - open - assigned - in_progress - completed -
cancelled

The initial workflow remains:

open -> assigned -> in_progress -> completed

Job acceptance must eventually perform the assignment creation and
request status change as one controlled/atomic operation.

The browser has intentionally NOT been given unrestricted assignment
creation permission.

  -----------
  DONATIONS
  -----------

Donation status values: - available - reserved - collected - expired -
cancelled

A separate donation_images table was added because a donation may
contain multiple images.

Actual image files belong in Supabase Storage. The database stores
Storage paths/metadata rather than raw image blobs.

  ---------
  REPORTS
  ---------

The reports table exists.

Official report workflow/status values have NOT yet been finalized by
the team.

Do not invent a more complex report status contract without documenting
and coordinating the decision.

  ---------------
  NOTIFICATIONS
  ---------------

The notifications table exists.

Users can access their own notifications according to RLS.

Browser users are intended to update only notification read state rather
than arbitrary notification content.

  --------------------
  ROW LEVEL SECURITY
  --------------------

RLS has been enabled on user-sensitive application tables.

Policies were added for ownership and role-based access.

Important security principles: - Users can access their own profile
according to policy. - Users cannot promote themselves to admin through
the frontend. - Users cannot change protected assistant
verification/training fields through ordinary browser access. -
Community users can create their own requests. - Donation ownership is
enforced. - Assignment access is restricted. - Reports are user-owned. -
Notifications are user-owned. - Admin access is broader where explicitly
permitted. - Verified-assistant access is checked using trusted database
state.

Never replace database/RLS authorization with hidden frontend buttons.

  -------------------------
  MIGRATION 002 - STORAGE
  -------------------------

Created/configured these Supabase Storage buckets:

1.  avatars - PUBLIC
2.  donation-images - PUBLIC
3.  verification-documents - PRIVATE

Verification documents MUST remain private.

Expected Storage path conventions:

avatars//avatar.ext

donation-images///image.ext

verification-documents//document.ext

Storage policies restrict authenticated uploads/changes to the
appropriate user’s UUID folder.

Do not expose verification documents through permanent public URLs.

  ------------------------------------
  MIGRATION 003 - DEVELOPER ACCOUNTS
  ------------------------------------

A dedicated developer_accounts table was added.

Purpose: Allow trusted project developers to use a Developer Mode
interface for testing without hard-coding developer email addresses,
passwords, or identifiers into public frontend source code.

Structure: developer_accounts - user_id - created_at

developer_accounts.user_id references profiles.id.

RLS is enabled.

An authenticated user may check whether THEIR OWN user_id exists in
developer_accounts.

There are intentionally no public/browser INSERT, UPDATE, or DELETE
policies for developer_accounts.

A browser user MUST NOT be able to grant themselves developer access.

Developer access is assigned through a trusted administrative/database
operation.

Do NOT commit developer email addresses or personal UUIDs into migration
files.

  --------------------------
  DEVELOPER ACCOUNT DESIGN
  --------------------------

“Developer” is NOT a normal application role.

Application roles remain: - community_user - assistant - admin -
organisation

Developer capability is separate.

A development account may, for testing purposes, have: - profiles.role =
admin - assistant.verification_status = verified -
assistant.training_status = completed - assistant.availability =
available - a row in developer_accounts

This allows one trusted development account to exercise the Admin and
Verified Assistant interfaces while Developer Mode can also display the
Community User interface.

IMPORTANT: Developer Mode must NEVER change profiles.role merely because
the developer switches the interface being viewed.

There is a critical distinction between:

1.  REAL AUTHORIZATION Stored/enforced by Supabase, profiles,
    assistants, developer_accounts, and RLS.

2.  CURRENT DEVELOPER VIEW Which frontend/dashboard the developer is
    currently testing.

Changing Developer Mode view must not grant new database permissions.

  ----------------------------
  DEVELOPER MODE UX DECISION
  ----------------------------

After login:

Normal users: - Load authenticated session. - Load trusted
profile/assistant state. - Redirect to the correct normal dashboard. -
Do not show Developer Mode.

Developer-authorized users: - Detect their own row in
developer_accounts. - May be sent to a Developer Mode selector. - May
choose which interface to test: - Community User - Verified Assistant -
Administrator

The existing role-selection-style frontend may be repurposed for the
Developer Mode selector if compatible with the current code.

Developer users should also have a small floating Developer Mode button
available while testing dashboards.

The floating button should allow switching between Community User,
Verified Assistant, and Administrator interfaces without logging out.

This button must only be shown after trusted developer authorization has
been confirmed.

Hiding/showing this button is UX only. Supabase/RLS remains responsible
for actual authorization.

Do NOT implement developer detection by hard-coding emails. Do NOT
hard-code a developer password. Do NOT put personal developer UUIDs into
frontend source code.

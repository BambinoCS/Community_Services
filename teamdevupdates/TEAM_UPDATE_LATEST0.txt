----------------------------------------------------------------
WHAT WE WORKED ON
----------------------------------------------------------------

Started from the existing repo (which only had partial Community
User pages, and empty stub files for Verified Assistant / Admin).
Inspected everything first, preserved all existing working code,
and then built out the remaining frontend for all three user roles
plus a small shared JS utility layer, following the architecture
already in place (HTML + inline <style> + separate .js files, no
frameworks, ready for later Node/Express + Supabase integration).

Nothing here is connected to a real backend yet. Every form/action
validates on the frontend, builds the payload the backend will
eventually expect, and then shows a clear "validated, not yet
submitted" message instead of pretending anything was saved.

FEATURES COMPLETED (FRONTEND ONLY)
----------------------------------------------------------------
- Full client-side validation on every form (required fields, max
  description length, positive integer quantities, date-not-in-past,
  date range checks, image type/size checks)
- Consistent status badges using ONLY the official lowercase DB
  values from MASTER_AI_TEAM_CONTEXT.txt (open, assigned,
  in_progress, completed, cancelled, pending, verified, rejected,
  suspended, not_started, available, unavailable, etc.) with
  human-readable labels layered on top
- Empty / loading / error / success states everywhere, using the
  exact wording requested (e.g. "No active requests yet.",
  "No statistics available yet.", "No community requests are
  currently available.")
- Assistant verification gating on "Accept Request" (frontend UX
  only - clearly noted that backend/RLS must enforce the same rule)
- Confirmation dialogs before any status-changing action (start job,
  complete job, approve/reject/suspend assistant, cancel request)
- Assistant profile page shows verification/training STATUS only -
  no documents are ever displayed
- Admin dashboard shows "No statistics available yet" instead of
  fake numbers; Admin Requests page only allows View + Cancel (no
  arbitrary status changes)

----------------------------------------------------------------
BACKEND / API DEPENDENCIES (NOT YET CONNECTED)
----------------------------------------------------------------
- POST /api/reports          (Report a Problem)
- POST /api/requests          (Request Service / Request New Items)
- POST /api/donations         (Donate form)
- POST /api/assignments       (Accept Request)
- PATCH /api/requests/:id     (status transitions: assigned ->
                                in_progress -> completed / cancelled)
- PATCH /api/assistants/:id   (verification status, availability,
                                training status)
- Supabase Storage buckets for donation images and assistant
  profile pictures
- GET endpoints for every list/dashboard/admin view (currently all
  start from empty arrays with a TODO comment above them)
- Supabase Auth + role-based redirect (login -> session -> profile
  -> role -> redirect) is not implemented yet

Every place a real API call will eventually go has a
"// TODO: connect to <METHOD> /api/..." comment directly above it,
so the next person (human or AI) can search for "TODO: connect to"
to find every integration point.

======================================================================
1. PROJECT OVERVIEW
======================================================================

Project Name:
Community Service Delivery Platform

Problem:
Many communities face linked problems such as unemployment, limited access to food,
water, clothing, school supplies, transport, healthcare, and other essential services.

Some businesses, organisations, government programmes, sponsors, and individuals
have resources available to help, but there is often no efficient system connecting
available resources to the people who need them.

At the same time, unemployed or underemployed community members may be willing
and able to assist others but lack structured opportunities, training, verification,
and a trustworthy way to connect with people who need support.

The platform should connect:
- Community users who need help
- Community users who want to donate resources
- Verified assistants who can perform approved services
- Administrators who manage, verify, and supervise the platform
- Organisations / sponsors / donors later if added

Main outcomes:
- Safety
- Employment
- Access to resources
- Community support

Important:
Verified assistants are helpers, not police or law-enforcement officers.

10. ROW LEVEL SECURITY
======================================================================

RLS should be enabled on user-owned or sensitive tables.

Examples of intended policy logic:

Profiles:
- Users can read their own profile
- Users can update their own profile
- Admins may have broader access

Requests:
- Community users can create requests
- Users can view their own request history
- Verified assistants can view eligible open service requests
- Only appropriate users/admins can change sensitive statuses

Donations:
- Users can create donations
- Users can edit their own donations
- Public/community browsing rules should be explicitly defined

Assignments:
- Assistants should only see assignments relevant to them
- Sensitive status changes should be protected

Never rely only on hiding buttons in the frontend for security.
Real permissions must be enforced with backend checks and/or Supabase RLS.

  "quantity": 3,
  "location": "Hatfield",
  "availableFrom": "2026-09-27T10:00",
  "availableUntil": "2026-09-28T17:00"

Example service request payload:

{
  "requestType": "service",
  "category": "grocery_collection",
  "description": "Need help collecting groceries",
  "location": "Example area"
}

If field names change, announce the change to the team.
Do not silently rename payload fields because it breaks other people's code.

20. FIRST END-TO-END SYSTEM FLOW TO BUILD
======================================================================

Do not try to build every feature at once.

Recommended first complete workflow:

1. User registers
2. User logs in
3. User opens Community User Dashboard
4. User selects Request Help
5. User creates a service request
6. Request is saved in Supabase
7. Verified Assistant Dashboard shows eligible open request
8. Verified assistant accepts request
9. Assignment row is created
10. Request becomes ASSIGNED
11. Assistant marks job IN_PROGRESS
12. Assistant marks job COMPLETED
13. Community user sees completed status in request history

This gives the project a complete working vertical slice.

Second recommended flow:

1. User opens Donate
2. User enters item details
3. User uploads images
4. Images go to Supabase Storage
5. Donation metadata is saved to database
6. Other users can browse available donations
7. Donation can later be reserved / collected

======================================================================
25. ERROR HANDLING
======================================================================

Backend responses should be predictable.

Example success:

{
  "success": true,
  "data": {...}
}

Example error:

{
  "success": false,
  "error": "Human-readable message"
}

Use proper HTTP status codes later:
- 200 OK
- 201 Created
- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict
- 500 Internal Server Error

Frontend should show readable messages to users instead of raw database errors.
